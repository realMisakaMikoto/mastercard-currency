## 改动

### 1. 汇率显示不再截断到 6 位

万事达返回的 `conversionRate` 是 **7 位小数**（如 `6.6991000`），而此前显示层用
`setScale(6, HALF_UP)` 砍到 6 位。后果是：**拿屏幕上的汇率自己乘一遍，尾数可能和「合计」对不上**。

例如实际汇率 `1.0000005`、金额 100,000：

- 官方总额 100,000.5
- 用屏幕上被截断的 `1.000001` 自己乘 → 100,000.1

现在直接展示接口返回的完整精度（仅去掉无意义的尾随零）。

### 2. 换算结果不再取整，完整显示小数位

此前换算结果会按目标货币的 ISO 4217 小数位做 `HALF_UP` 取整（CNY 2 位、JPY 0 位、KWD 3 位）。
现在**完全不取整**，直接给出精确乘积，只去掉尾随零。

实测（USD → CNY，汇率 6.6991）：金额 `12345.67`

```
换算为  82,704.877897
```

`12345.67 × 6.6991 = 82,704.877897` —— 与手算逐位一致。

未改金额时仍采用万事达返回的 `crdhldBillAmt`（官方总额），同样不取整：
`66991.0000000` 显示为 `66,991`。

### 影响与取舍

- **小数位不再按货币规范化**：JPY 结果可能带小数、KWD 可能只有 1 位小数。这是「不取整」的必然结果。
- `Currency.minorUnits`（ISO 4217 精度）**保留在数据集里**并仍有测试校验，
  但不再参与换算结果的显示 —— 将来若需要规范化显示可以直接启用。
- 手续费金额同样不再取整，以保持明细与总额能对得上。

### 未修复（按你的要求跳过）

`crdhldBillAmt` 字段缺失时会被兜底成 `0`，而 UI 的判断是 `signum() >= 0`，
因此该情况下会显示 `0` 而不是退回本地相乘。**已知悉并保留。**
